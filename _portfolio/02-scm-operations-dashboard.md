화장품·식품·의류·생활가전·선물상품 5개 상품군의 화주사를 한 센터에서 운영하는 3PL을 가정하고, 입고·검수·재고·피킹·패킹·출고·반품·인력·정산을 한곳에서 확인하도록 만든 운영 대시보드다. 다품종 소형가전 3PL 센터 등 물류센터 운영 경험을 바탕으로 기준을 정하고 가상 데이터로 구현했다. 모든 상품군의 센터에서 근무했다는 뜻은 아니다.

## 한눈에 보기

| 수치 | 의미 |
|---|---|
| **5 / 5** | 일부러 넣은 정산 오류를 찾아냄 (원인 4유형 · 가상 데이터 기반 테스트) |
| **447,538** | 계산 점검 항목 모두 통과 (가상 데이터 기반 자동 점검) |
| **227** | 화면 숫자 점검 항목 통과 (가상 데이터 기반 자동 점검) |
| **0건** | 120개 화면 조합 오류 (PC·모바일 · 점검 스크립트로 재확인) |

## 배경 · 문제

- 다화주 3PL 센터는 화장품·식품·의류·가전처럼 성격이 다른 상품을 한 센터에서 함께 다룬다. 상품군마다 입고 검수 항목, 보관 조건, 출고 배정 규칙(FEFO/FIFO), 세트 구성, 반품 판정 기준이 달라 하나의 표로 운영 상황을 판단하기 어렵다.
- 입고 수량 부족, 실사 차이, 오출고·재출고, 반품 적체 같은 문제의 원인이 입고·재고·출고·반품 자료에 흩어져 있어, 어느 공정에서 생긴 문제인지 거슬러 찾는 데 시간이 걸린다.
- 월말에는 화주사별 정산 초안을 실적과 맞춰야 하는데, 취소된 송장이나 센터 귀책 재출고가 청구에 섞이거나 계약 단가가 잘못 들어가도 수작업 대조로는 놓치기 쉽다.
- 이 상황은 특정 회사의 실제 데이터가 아니라 3PL·풀필먼트 센터에서 입출고·재고·작업관리·화주사 정산을 해 온 경험을 바탕으로 가정한 운영 환경이다.

## 목표

- 모든 상품군에 같은 기준으로 계산할 수 있는 공통 지표(입고 수량, 출고 건수, 당일 출고율, 재고 정확도, 오출고율, 반품 건수)와 소비기한·옵션·세트처럼 상품군마다 다른 지표를 나눠, 기준이 다른 숫자를 합산하지 않는 것을 목표로 했다.
- 입고 → 검수 → 적치 → 재고 → 피킹 → 패킹 → 출고 → 반품 순서로 화면을 배치해, 문제가 생긴 공정을 따라가며 확인할 수 있게 하는 것을 목표로 했다.
- 화주사별 월 정산 초안을 입고·출고·반품 실적으로 다시 계산해, 차이와 원인, 수정 근거까지 한 화면에서 보이게 하는 것을 목표로 했다.

## 데이터

- 실제 기업 데이터는 사용하지 않았다. 가상 물류센터 1곳, 5개 상품군(화장품·뷰티, 식품, 패션·의류, 생활용품·소형가전, 주얼리·선물상품)의 가상 화주사 5곳, 49개 품목(세트·구성품 포함), 보관 존 6개, 판매 채널 4개와 단가·인력·표준 처리량은 모두 가정값이다.
- js/data.js가 시드 고정 난수로 2026-05-01 ~ 2026-10-28(181일)의 주문 41,213건, 입고 278건, 로트 368개와 반품을 만들고, 하루 단위로 입고·검수 → 주간 실사 → 주문 접수 → 피킹·송장 → 검수·포장 → 출고 확정·재고 반영 → 반품 → 발주를 계산한다. 재고는 로트마다 실물과 전산을 따로 기록한다.
- 가상 운영 시나리오 8개(상품군별 행사 집중, 수입 입고 지연, 7/1 운영 개선 가정, 출고 확정 전산 누락, 잔여 소비기한이 짧은 입고분, 시즌 전환, 신규 작업자 오출고, 월 정산 초안 오류)를 넣어 문제 상황이 지표에 나타나게 했다.
- 월 정산 초안(가상)에는 5개 화주사의 서로 다른 달에 오류 5건(송장 발행 후 취소 건 청구, 센터 귀책 재출고 청구, 세트 조립 단가 오적용, 반품 처리 단가 오적용, 보관 수량 과다)을 일부러 넣었다.
- 실제 경력과의 연결: 생활용품·소형가전은 제이아이로지스 다품종 소형가전 3PL 센터 경력, 식품은 젠미코리아의 수입식품 통관·출고 데이터 경력과 연결된다. 나머지 상품군의 운영 사례는 시뮬레이션이다.
- 현재는 시뮬레이션 데이터 기반으로 구현했으며, 실제 운영 환경에서는 ERP/WMS/TMS API 또는 데이터베이스와 연동할 수 있도록 확장할 수 있다.

## 해결 방법

- 상품군별 운영 기준을 데이터로 정리: 검수 항목, 보관 조건, 출고 배정 규칙(FEFO/FIFO), 세트 구성(BOM), 반품 판정 등급을 상품군 설정 한 곳에서 관리하고, 상품군을 고르면 모든 화면의 숫자와 기준이 그 화주사 기준으로 바뀌게 했다.
- 로트 단위 실물·전산 재고: 실물(판매 가능·격리)과 전산 재고를 따로 기록하고, 둘이 어긋나는 사건(출고 확정 전산 누락, 파손 등)을 차이 기록으로 남겨 주간 실사 차이를 원인까지 추적할 수 있게 했다.
- 공정별 표준 처리량(UPH)으로 필요 인력을 계산하고, 패킹 능력을 넘긴 주문은 다음 날 출고로 넘겨 행사 기간의 병목이 당일 출고율과 연장·임시 인력에 나타나게 했다.
- 정산 대조 5단계: 실적 재계산 → 초안 비교 → 차이 발견 → 원인 분류 → 수정 근거. 원인은 초안의 비고가 아니라 송장 취소·재출고 귀책·계약 단가 기록으로 판정해, 화주사에 설명할 근거(주문번호·단가)를 함께 보여 주게 했다.

## 주요 기능

- 데모 소개와 실제 경력 연결: 현장 업무마다 "직접 해 온 일"(이력서 기준 실제 경력)과 "데모에서 보여 주는 것"(시뮬레이션)을 나눠 적어, 보는 사람이 경력과 가상 데이터를 혼동하지 않게 했다.
- 종합 풀필먼트 현황: 공통 지표 6개, 상품군 비교, 주별 주문·출고, 지금 확인할 일을 한 화면에 모아 센터 전체 상황과 먼저 볼 문제를 바로 확인할 수 있게 했다.
- 입고·검수·적치와 재고·로케이션: 입고 예정 대비 부족, 상품군별 검수 불합격, 존별 적치율, 로트별 재고와 실사 차이의 원인을 보여 줘 재고 정확도가 떨어진 이유를 확인할 수 있게 했다.
- 피킹·패킹·출고와 인력·생산성: 로케이션 순 피킹리스트, 검수에서 잡은 오피킹, 공정별 UPH와 필요 인력 대비 투입 인력, 연장·임시 인력을 보여 줘 행사 기간 병목이 어느 공정에서 생겼는지 볼 수 있게 했다.
- 반품과 출고 이슈: 반품 회수·검수·상품군별 판정과 미출고·오출고·파손·재출고를 유형·귀책별로 정리해, 재출고 비용을 화주사에 청구할지 센터가 부담할지 구분할 수 있게 했다.
- 물류비·정산 대조: 화주사별 월 정산 초안을 실적으로 다시 계산해 차이 항목, 원인, 수정 근거(주문번호·단가)를 보여 주고 CSV로 내려받을 수 있게 했다.
- 상품군별 현장 기준: 선택한 상품군의 검수 항목, 보관 조건, 출고 배정 규칙과 전용 지표(소비기한 임박 재고, 옵션별 재고, 세트 조립 가능 수 등)를 보여 줘 상품군마다 다른 운영 기준을 확인할 수 있게 했다.

## 구조

- 서버·빌드 도구 없이 HTML·CSS·JavaScript로 만든 정적 웹 앱이다. 포트폴리오 사이트(Flask)에 포함해 /demo/scm-dashboard/ 경로로 제공하며, 사이트 보안 정책(CSP)에 맞춰 Chart.js를 사이트 안에 포함했다.
- 역할별로 파일을 나눴다: data.js(가상 데이터와 하루 단위 운영 계산) → metrics.js(필터·지표·정산 계산) → ui.js(카드·표·단계 등 공통 화면 요소) → charts.js(차트 공통 스타일) → export.js(숫자 서식·CSV) → app.js(10개 화면).
- 표는 하나의 열 정의로 화면·검색·페이지·CSV(UTF-8 BOM)를 함께 만들어, 화면 숫자와 내려받은 파일 숫자가 달라지지 않게 했다. 화면 숫자는 모두 metrics.js 계산 결과만 쓴다.
- 데이터베이스·로그인·서버 API는 없다. 모든 계산은 브라우저에서 실행된다.

## 역할

개인 프로젝트: 화면 구성(현장 흐름 순서, 상품군 전환), 실제 경력과 시뮬레이션을 나누는 표기 기준, 상품군별 운영 기준을 요구사항으로 정하고 결과를 검토했다. 코드 작성, 가상 데이터와 시나리오 생성 로직, 자동 점검 스크립트 작성과 브라우저 점검에는 AI 코딩 도구(Claude Code)를 활용했다.

## 시행착오

- 첫 점검에서 정산 원인이 4유형이 아니라 3유형만 나왔습니다. 무작위로 만든 데이터에서 8월 생활·가전 화주의 센터 귀책 재출고가 한 건도 생기지 않았기 때문입니다. 해당 주에 오출고 4건이 생기도록 시나리오를 고정해, 정산 대조가 이 오류 유형도 찾는지 확인할 수 있게 했습니다.
- 고친 뒤 다시 점검하자 특정 로트의 재고가 음수가 됐습니다. 오출고를 처리할 때 품목 전체 재고만 확인하고 첫 번째 로트에서 차감한 것이 원인이었습니다. 차감할 로트 자체에 수량이 충분한지 보도록 바꾼 뒤 447,538개 항목이 모두 통과했습니다.

## AI 활용 방식

- 제품 안에는 AI 기능이 없습니다. 지표와 정산 숫자는 AI 판단이 아니라 정해 둔 공식으로 계산합니다. AI는 만드는 과정에 썼고, AI가 만든 결과는 자동 점검과 직접 검토를 통과한 것만 반영했습니다.

**AI에 맡긴 일**

- 코드 작성 (화면 10개, 필터·표·차트·CSV)
- 가상 데이터·시나리오 생성 로직 구현
- 계산 점검·화면 점검 스크립트 작성과 실행
- 점검 실패 원인 분석과 수정안 제시

**직접 판단한 일**

- 요구사항 작성: 현장 흐름 순 화면, 상품군 전환, 실제 경력과 가상 데이터를 나누는 표기 기준
- 프로젝트 성격 결정: 실제 경력과 맞도록 패션 단일 업종이 아닌 다품종 다화주 3PL로 변경
- 불필요한 요소 제외 기준: AI가 덧붙이던 용어 풀이 화면을 넣지 않고 현장 용어를 그대로 쓰기
- 점검 결과 확인과 공개 여부 판단

**검증**

- AI가 작성한 계산을 그대로 쓰지 않았습니다. 자동 점검 447,538개 항목과 화면 숫자 227개 항목을 대조했고, 이 과정에서 시나리오 누락과 로트 재고 음수 오류 2건을 찾아 고쳤습니다.

## 결과

- 계산 일치 점검(Node.js, tests/multi3pl/check_consistency.js)에서 주문 단계, 상품군별 재고 규칙, 로트 재고 재계산(중복 차감 방지), 실사, 전체 = 상품군 합계, 반품, 입고, 정산, 필터 조합을 대조해 447,538개 항목이 모두 통과했다.
- 화면 숫자 점검(Playwright, tests/multi3pl/check_screen_numbers.py)에서 기간·상품군 조합 6가지마다 KPI·단계 숫자·차트·표·CSV를 계산 결과와 대조하고, 정산 대조가 넣어 둔 오류를 모두 찾는지와 검색·페이지 동작을 확인해 227개 항목이 모두 통과했다.
- 정산 대조 화면은 일부러 넣은 오류 5건을 모두 찾아 차이 9줄(+350,750원), 원인 4유형, 수정 근거 12건으로 정리했고, 수정 근거 금액의 합이 차이 금액과 맞는지도 확인했다.
- 10개 화면 × 상품군 6가지(전체 + 5개) × 화면 폭 2가지(1440px·390px), 120개 조합을 열어 가로 넘침·차트 누락·콘솔 오류가 0건인 것을 확인했다(2026-11-10 점검 스크립트 tests/multi3pl/check_combos.py로 다시 실행해 120개 모두 통과).
- 모든 수치는 가상 데이터이므로 실제 업무 시간 단축이나 비용 절감 효과는 검증하지 않았다. 실제 데이터를 연결하면 화주사별로 흩어진 실적과 정산 초안을 줄 단위로 대조하던 과정을 한 화면에서 확인하는 방식으로 줄일 수 있을 것으로 예상한다.

## 한계와 개선 과제

- 실제 운영에 쓰려면 브라우저에서 만드는 가상 데이터 대신 WMS·OMS·ERP·택배사(TMS) API나 데이터베이스에서 데이터를 받아오는 구조가 필요하다.
- 현재는 브라우저가 6개월치 주문 약 4만 건을 직접 계산한다. 화주사와 기간이 늘어나면 집계를 서버·데이터베이스로 옮겨야 한다.
- 상품군별 기준과 단가, 표준 처리량은 가정값이다. 실제 센터에 적용하려면 화주사 계약 단가, 실제 근태·작업 실적, 로케이션별 실재고로 다시 검증해야 한다.
- 실제 사용 환경이라면 로그인·권한, 정산 수정 이력 관리, 결품·마감 위험 알림 기능도 필요하다.
