반도체 수출을 준비하는 기업의 엑셀 자료(정해진 업로드 양식 또는 가상 샘플)를 바탕으로, 어느 나라에 팔기 좋은지와 가격·운송·규제·환율 안정성을 한 화면에서 비교해 보는 웹 서비스다. 5명이 함께 만든 팀 프로젝트이며, 그중 공공데이터 수집·가공, 다른 팀원이 개발한 분석 엔진을 서비스에 통합·연결하는 작업, 로그인 기능을 맡았다.

## 한눈에 보기

| 수치 | 의미 |
|---|---|
| **약 1주** | 동작하는 서비스 완성 (5인 팀, 09.23~09.29) |
| **466→221MB** | 공개 배포본 최대 메모리 (Windows 로컬 같은 시나리오 재측정 · 과거 커밋 기록은 215MB) |
| **47개** | 자동 테스트 통과 · 3개는 별도 Postgres DB 필요로 미실행 (2026-11-10) |
| **5개** | 분석 영역 통합 |

## 배경 · 문제

- 수출 기업이 새로운 국가로 제품을 수출하기 전 검토해야 하는 시장성·가격·물류·규제·환율 안정성 정보가 각각 다른 공공데이터·통계·공시 자료에 흩어져 있어, 이를 한 번에 확인하고 판단하기 어려웠다.

## 목표

- 수출 기업이 엑셀 데이터를 업로드하면 5개 영역을 자동으로 계산해 하나의 화면에서 참고할 수 있도록 만드는 것을 팀 목표로 했다.
- 개인적으로는 데이터 파이프라인 구축, 다른 팀원이 만든 분석 엔진의 통합·연결, 로그인·백엔드 시스템을 맡아 다른 팀원이 만든 화면 디자인과 결합되는 실제 동작 서비스로 완성하는 것을 목표로 했다.

## 데이터

- UN Comtrade, 관세청(KCS), 한국은행 ECOS, KOTRA, WTO, FRED 환율 등 실제 공개 공공데이터·공식 발간자료를 수집해 사용했으며, 출처와 해시값을 별도 파일(MANIFEST.csv)로 관리했다.
- 실제 기업 데이터는 구할 수 없어, 3개 가상 기업(대성일렉트로닉스·새벽반도체·한빛반도체)의 수출 데이터를 고정 시드로 직접 생성해 시연용 샘플로 사용했으며, 가상 데이터임을 엑셀 파일에 명시했다.

## 해결 방법

- 공공데이터를 수집→가공→검증→배포하는 데이터 파이프라인을 직접 구축하고, 다른 팀원이 개발한 5개 영역(시장성·가격·물류·안정성·규제) 분석 엔진을 서버 패키지로 옮겨 원본 자료 경로·업로드 파일·대시보드 문서 형식에 맞게 연결했다.
- 안정성 평가는 목적국 결제통화의 환율 변동성과 과거 10년 분포를 비교하는 산식을 팀 검토를 거쳐 설계했고, 시연용 종합 채점 산식(시장성 35·가격 30·물류 20·안정성 15 가중치, 규제는 감점형 관문)을 별도로 설계해 화면에 반영했다.
- Supabase를 이용한 회원가입·로그인·세션 관리와, 사용자별 작업 폴더·파일을 저장하는 워크스페이스 백엔드를 직접 구현했다.
- 팀원이 만든 정적 대시보드 디자인 시안에 실제 업로드 데이터를 연결해, 화면만 있는 시안이 아니라 실제로 동작하는 기능으로 완성했다.
- 제출 이후 포트폴리오 공개를 위해 팀 배포본과 별도의 공개 배포본을 만들었다. 채용 담당자가 가입 없이 체험하도록 로그인 대신 브라우저별 방문자 세션으로 업로드·분석·바탕화면 저장이 되게 했고, 익명 사용을 고려해 IP별 요청 제한·업로드 5MB 상한·마지막 사용 후 7일 자동 삭제를 넣었다. 개인에게 발급된 외부 기관 API 키는 공개 서버에 두지 않고, 그 영향을 화면 안내로 밝혔다. 로그인 제외·키 제외 같은 공개 기준은 직접 정했고, 구현과 점검에는 AI 코딩 도구(Claude Code)를 활용했다.

## 주요 기능

- 엑셀 업로드(드래그 앤 드롭)와 기업명·HS코드·대상국 입력을 실제 분석 엔진에 연결해, 팀원이 만든 정적 화면 시안을 실제로 동작하는 기능으로 완성했다.
- 시장성·가격·물류·안정성·규제 5개 영역을 탭으로 구분해 보여주고, 값마다 계산 출처와 결측 여부를 함께 표시해 실제 데이터 기반 값과 아직 비어있는 값을 구분할 수 있도록 했다.
- 영역별 가중치를 사용자가 조정하되 합계 100%를 검증하도록 만들어, 기본 기준(시장성 35·가격 30·물류 20·안정성 15)을 상황에 맞게 바꿔볼 수 있도록 구성했다.
- 회원가입·로그인·로그아웃과 사용자별 작업 폴더 저장 기능을 구현해, 재로그인해도 이전 작업 폴더가 유지되도록 했다.
- 문의하기 접수 기능에 스팸 방지(허니팟, IP당 분당 3회 제한)를 적용해 최소한의 남용 방지 장치를 뒀다.

## 구조

- Flask 단일 서버 구조이며, 서버 진입점이 팀원별로 각자 브랜치에서 개발한 모듈(개인 담당: 로그인·워크스페이스, 분석 엔진 통합·연결 / 다른 팀원 담당: 분석 엔진 개발, 홈 화면, 대시보드 초기 디자인, 챗봇 위젯)을 임포트해 통합하는 구조다.
- 팀원별로 별도 폴더에서 작업한 뒤 Git 브랜치와 Pull Request로 병합하는 방식으로 협업했다.
- 로그인은 Supabase(외부 인증 서비스)를 사용하고, 세션 정보는 로컬 SQLite에 저장했다. 분석 결과도 별도 SQLite에 누적 저장된다.
- 프런트엔드는 프레임워크 없이 Jinja2 템플릿과 Vanilla JS로 구성했고, 차트는 Chart.js를 로컬로 포함해 사용했다.
- AI 챗봇은 OpenAI API 연동을 지원하되 데모/라이브 모드를 전환할 수 있도록 구성했다(챗봇 구현 자체는 다른 팀원 담당).
- 팀 배포본과 별도로, 포트폴리오 공개 배포본을 Render 무료 플랜(gunicorn 1 worker)에서 운영한다. 이 배포본은 로그인을 쓰지 않고 방문자 데이터를 서버 디스크(SQLite)에 저장하며, 외부 기관 API 키를 넣지 않았다.

## 내 기여와 팀의 역할

**내가 맡은 일**

- 공공데이터 수집·가공 파이프라인 설계
- 다른 팀원이 개발한 분석 엔진(5개 영역, 13개 이상 모듈)을 서버에 통합하고 업로드·대시보드와 연결
- 로그인·계정·워크스페이스 백엔드(Supabase 연동)
- 문의하기 백엔드
- 대시보드 화면에 실제 데이터를 연결하는 프런트엔드 로직 구현

**다른 팀원이 맡은 일**

- 분석 엔진(시장성·가격·물류·안정성·규제) 개발
- 홈 화면 디자인
- 대시보드 초기 시안
- 챗봇 위젯 연동

## 시행착오

- 무료 서버(메모리 512MB)에서 분석 중 서버가 강제 종료됐습니다. 단계별로 메모리를 재서 한국은행 엑셀 속 약 30MB 외부 링크 데이터를 함께 읽는 것이 원인임을 찾았고, 읽는 값은 같게 유지한 채 최대 메모리를 466MB → 221MB로 줄였습니다(2026-11-10 Windows 로컬 같은 시나리오 재측정, 과거 커밋 기록은 215MB).

## AI 활용 방식

- 서비스 안의 AI 챗봇(OpenAI)은 다른 팀원이 맡았습니다. 제가 담당한 기능에는 AI가 들어가지 않습니다.

**AI에 맡긴 일**

- 공개 배포본 구현과 점검
- 메모리 문제 진단·수정 (함께 진단)

**직접 판단한 일**

- 공개 기준 결정: 로그인 제외, 외부 기관 API 키 제외
- 데이터 수집 → 가공 → 검증 → 배포 흐름과 출처 관리
- 다른 팀원이 만든 분석 엔진을 업로드·대시보드와 연결

**검증**

- 화면의 값마다 계산 출처와 결측 여부를 표시하고, 키가 없는 지표는 ‘판단 근거 부족’으로 보여 줘 근거 없는 점수를 내지 않게 했습니다.

## 결과

- Playwright 기반 브라우저 회귀 테스트 스크립트를 직접 작성해, 업로드→분석→영역별 표시→필터→로그인→폴더 관리→로그아웃 후 재로그인까지의 흐름과 브라우저 콘솔 오류 0건을 반복적으로 확인했다.
- 팀이 검토·확정한 안정성 평가 산식(환율 변동성 기반)은 문서화했지만, 이번 제출 시점 엔진 점수 계산에는 아직 전부 반영하지 못한 부분이 있어 이는 완료가 아닌 진행 중인 상태로 남겨둔다.
- 미니프로젝트 제출 기준으로 로그인, 파일 업로드, 5개 영역 분석 표시, 문의하기까지 하나의 흐름으로 동작하는 것을 확인했으며, 아직 채용 담당자나 실제 사용자에게 공개해 반응을 확인한 단계는 아니다.
- 공개 배포본을 무료 서버(메모리 512MB)에서 분석하던 중 서버가 강제 종료되는 문제가 있었다. 단계별 메모리 측정으로 원인이 한국은행 원표 엑셀에 포함된 약 30MB의 외부 링크 데이터를 함께 읽는 데 있음을 찾아, 읽는 값은 같게 유지한 채 최대 메모리를 줄였다(AI 코딩 도구와 함께 진단·수정). 2026-11-10 Windows 로컬에서 같은 시나리오로 수정 전후를 다시 측정하면 466MB → 221MB이고 분석 결과는 같다(junhee/docs/MEMORY_MEASUREMENT.md). 2026-10-06 커밋 메시지에는 215MB로 기록되어 있으나 당시 원시 로그는 없다. 로컬 측정이라 Render 서버의 실제 수치와는 다를 수 있다.
- 공개 배포본 코드는 로컬에서 자동 테스트 47개 통과·3개 미실행(별도 Postgres 테스트 DB가 있어야 실행되는 테스트, 2026-11-10 재실행), 외부 API 키 없이 가상 샘플과 업로드 양식 파일의 분석 완료, 방문자 간 데이터 분리를 확인했다. 키가 없는 지표는 ‘키 없음’으로 표시되어 종합 등급은 ‘판단 근거 부족’으로 나온다.

## 한계와 개선 과제

- 팀이 확정한 안정성 평가 산식과 실제 엔진에 반영된 계산이 다른 부분이 있어, 이를 일치시키는 정리가 필요하다.
- 물류 영역은 실제 공항·항만 API 연동 전이라 일부 가정값을 사용했다 — 향후 실제 운항 데이터 API 연동이 필요하다.
- 현재는 정해진 업로드 양식(v1)과 등록된 샘플 형식의 엑셀만 분석된다. 양식이 다른 임의의 기업 엑셀을 읽어 들이는 기능은 향후 과제다.
- 현재 배포 환경 특성상 문의하기 접수 내역이 재배포 시 사라질 수 있어, 실제 서비스라면 외부 저장소로 옮길 필요가 있다.
- 실제 기업 데이터 기반 검증과 수출 규제 판정의 법적 정확성 검토는 아직 수행하지 않았다.
- 공개 배포본은 외부 API 키를 넣지 않아 일부 지표가 ‘키 없음’으로 나오고, 무료 서버 디스크를 쓰기 때문에 재시작·재배포 시 방문자 작업이 사라진다. 실제 서비스라면 키 관리(비밀 저장소)와 외부 저장소·사용량 모니터링이 필요하다.
